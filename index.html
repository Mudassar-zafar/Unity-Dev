02 · Show architecture

One laptop. Two screens. Zero dependencies.

The whole show is one Unity application on one Windows x64 machine. The operator console and the big-screen show are two displays of the same process, sharing state directly. No cloud, no backend, nothing that can fail on venue Wi-Fi.

Host
Operator laptop · Windows x64 · single Unity app · kiosk shell
Kiosk shell: auto-launch on boot, single-instance guard, watchdog relaunch on any fault, display assignment remembered per venue. auto-recovery in seconds, no operator panic

RISK: board unplugged mid-ride. A rider steps off, a cable snags. This is a live event; it will happen.
HANDLED: a device-lost event pauses the ride (timer frozen, score kept), the big screen shows a calm hold state, the console prompts the operator. Reconnect resumes in place. The show loop never exits.
Risk register

What can misfire, and what is already planned for it

RiskWhy it mattersMitigation, built into the plan
R1HDRP frame budget on one laptop AAA water plus VFX plus two displays on a single kiosk machine is the hardest technical constraint in the brief. Performance budget from week 1. A profiling gate at every milestone, and scalable quality tiers so the look degrades gracefully, never the frame rate.
R2Steering feel does not match the prototype Feel is the product. If leaning feels off, nothing else matters. A dedicated feel-tuning milestone (week 4) with the real board, side by side against your prototype. Dead-zone and response curve exposed as data, not code.
R3Venue display surprises Projectors, LED walls and resolutions differ at every event. Display assignment memory plus a windowed fallback and an operator hotkey to re-target screens. The watchdog recovers the show in seconds.
R4Parity drift from the PRD A complete spec only pays off if the build is held against it. Your named screen catalog becomes the QA checklist. Every milestone closes with a screen-by-screen check against the prototype, so drift is caught in days, not at delivery.
